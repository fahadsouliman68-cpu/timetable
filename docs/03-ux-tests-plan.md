# 03 — الشاشات، PDF والنسخ الاحتياطي، الاختبارات، المخاطر، خطة التنفيذ

> هذا مستند تصميم. كل ما يلي مقترح ما لم يُذكر أنه مُنفَّذ. الحالة الفعلية في `docs/STATUS.md`.

## 8. الشاشات وخريطة التنقل

### 8.1 خريطة التنقل (Navigation Compose)
```
[الرئيسية]
 ├─ الإعداد (المعالج، يُفتح عند أول تشغيل ويبقى متاحاً)
 │   ├─ المدرسة والعام
 │   ├─ الصفوف والشعب
 │   ├─ المواد والخطة
 │   ├─ المعلمون (المواد، النصاب، التوفر)
 │   └─ الورديات والأيام والحصص والاستراحات
 ├─ التكليفات والأنصبة
 ├─ قواعد الجدولة
 ├─ الجدول
 │   ├─ عرض (مدرسة/صف/شعبة/معلم/مادة)
 │   ├─ المحرر اليدوي
 │   ├─ التوزيع التلقائي (تقدّم، إلغاء، نتيجة)
 │   └─ التعارضات والنواقص
 ├─ المسودات والإصدارات (اعتماد، مقارنة، استعادة)
 ├─ التقارير (لوحة المعلم، الصفوف، الشعب، المواد، الاكتمال)
 ├─ الطباعة وPDF
 ├─ النسخ والاستعادة
 └─ سجل التعديلات
```
الشاشات الرئيسية الأربع في شريط سفلي: الرئيسية، الجدول، التكليفات، التقارير. البقية من القائمة الجانبية.

### 8.2 وصف الشاشات الحرجة
| الشاشة | المحتوى | الإجراء الأساسي | قيود تفعيل الأزرار |
|---|---|---|---|
| الرئيسية | نسبة الاكتمال، عدد التعارضات الصلبة، النواقص، آخر إصدار معتمد | ينقل إلى أول مهمة ناقصة | لا شيء |
| التكليفات | لكل شعبة: مادة، معلم، حصص، مجموع مقابل الخطة | تعديل تكليف، اقتراح معلم الصف | المعلم لا يُدرِّس مادة غير مسموحة (تظهر في القائمة مُعطَّلة مع السبب) |
| المحرر اليدوي | شبكة الأسبوع لشعبة، تحديد خانة، اختيار مادة ومعلم | وضع الحصة | زر "حفظ" معطّل حتى يمر الفحص، ويظهر السبب |
| التوزيع التلقائي | فحص الجدوى أولاً، ثم تقدّم، ثم نتيجة أو سبب الفشل | بدء، إلغاء، حفظ كمسودة | "بدء" معطّل عند فشل الجدوى مع السبب |
| الاعتماد | تقرير المدقق كاملاً | اعتماد | معطّل عند أي خطأ صلب أو نقص، مع قائمة ما يمنع |
| الإصدارات | قائمة بالأرقام والتواريخ والجودة | مقارنة إصدارين، استعادة (تُنشئ مسودة) | لا تُعدَّل إصدارات معتمدة |

### 8.3 عرض الجدول على الهاتف بـ RTL
- الأيام تقرأ من اليمين إلى اليسار: الأعمدة أيام، الصفوف حصص، والحصة الأولى في الأعلى.
- شاشة هاتف عرضها نحو 360dp لا تتسع لأسبوع كامل بخمسة أيام وستة حصص مع الأسماء. الحل:
```
[ يوم ▼ ]  (اختيار يوم واحد يعرض جدوله عمودياً)
 ┌──────────────────────────┐
 │ 1  الرياضيات   · أ. أحمد │  (الحصة، المادة، المعلم)
 │ 2  العربية     · أ. سمر  │
 │ 3  ⚠ فراغ                │  (شكل + نص، لا لون فقط)
 │ 4  🔒 العلوم   · أ. خالد │  (مقفل)
 └──────────────────────────┘
 [ عرض الأسبوع كاملاً ] ← شبكة أفقية قابلة للتمرير، الأرقام لاتينية
```
- شبكة الأسبوع الكاملة تُعرض أفقياً مع تمرير، والعمود الأول (الحصص) ثابت.
- الألوان مرفقة بأيقونات وأسماء: أخضر صحيح (✓)، أحمر تعارض (⛔)، أصفر ناقص (•)، رمادي فارغ (—)، أزرق مقفل (🔒).

### 8.4 عرض التعارضات
```
⛔ تعارض صلب — المعلم أ. أحمد في مكانين
   الصف 1/أ، الاثنين، الحصة 2
   التكليف: الرياضيات لـ 1/أ (4 حصص)
   [ الانتقال إلى الخانة ]  [ تجاهل؟ لا: الخطأ الصلب لا يُتجاهل ]
```
الخطأ الصلب لا يُتجاهل. النقص يظهر بنص "ناقص: 2 من 4" ويُسمح به في المسودة فقط.

### 8.5 حالات التحميل والفراغ والخطأ
| الحالة | الشاشة | النص المعروض |
|---|---|---|
| تحميل | أي شاشة قوائم | هيكل عظمي (skeleton) بدل الشريط الدوّار |
| فراغ | التكليفات قبل إدخال الخطة | "لم تُدخل الخطة بعد. ابدأ بـ الصفوف ثم المواد." مع زر الانتقال |
| فراغ | الجدول بلا مسودة | "لا توجد مسودة. ابدأ بالتوزيع التلقائي أو أنشئ مسودة يدوية." |
| خطأ قاعدة بيانات | أي شاشة | "تعذّر الحفظ، لم يتغيّر شيء. حاول مرة أخرى." (لا يُعرض اسم الاستثناء) |
| فشل التوزيع | التوزيع | سبب الاستحالة، القيود المانعة، والمعلمون والشعب المتأثرون |

### 8.6 مخططات الحالة (Draft / Final)
```
DRAFT ──تعديل──▶ DRAFT
  │                 ▲
  │ اعتماد (Validator: 0 صلب، 0 نقص)
  ▼
FINAL ──تعديل──▶ ينشئ DRAFT جديداً منسوخاً (FINAL لا يتغيّر)
  │
  └── اعتماد جديد ⇒ الأول يصبح ARCHIVED
```

## 9. PDF العربي والنسخ الاحتياطي

### 9.1 PDF (مقترح تقني)
- **الخيار المُقترح:** `android.graphics.pdf.PdfDocument` مع رسم النص عبر `StaticLayout` بخط عربي مضمّن (مثل Noto Naskh Arabic أو Noto Sans Arabic) داخل التطبيق، لا من النظام، لضمان الاتساق.
- **الاتجاه:** `TextDirectionHeuristics.RTL`، والمحاذاة يمين. الأرقام تُكتب بالإنجليزية (1 2 3) كما يطلب التصميم، لذا تُرسم ككتلة LTR منفصلة داخل سطر RTL.
- **الاتصال:** الحروف العربية تُوصل تلقائياً عند الرسم عبر خط عربي. يجب اختبار كل خط يُضمَّن بنص حقيقي قبل الاعتماد.
- **التخطيط:** A4 بالحجم 595×842 نقطة، هوامش، ترويسة (اسم المدرسة، الشعار، العام)، تذييل (رقم الصفحة من/إلى، تاريخ الإصدار بالأشهر السورية).
- **البديل المرفوض:** WebView وHTML للطباعة، لأنه يضيف اعتماداً على محرك متصفح ويصعب قياس الحجم والصفحات بدقة.
- **التحقق:** يُفتح الملف الناتج على أكثر من عارض PDF، ويُقارن بلقطة مرجعية. لا يُقبل إلا إذا لم تنكسر أي كلمة عربية.

### 9.2 النسخ الاحتياطي
- **الصيغة:** ملف JSON بترويسة:
```json
{
  "schemaVersion": 1,
  "appVersion": "1.0.0",
  "createdAt": "2026-11-14T17:00:00+03:00",
  "checksum": { "algorithm": "SHA-256", "value": "…" },
  "encryption": { "enabled": false },
  "data": { "school": {…}, "years": […], "…": "…" }
}
```
- **السلامة:** SHA-256 على حقل `data` بعد التسلسل بترتيب مفاتيح ثابت. الملف الذي لا يطابق checksum يُرفض قبل أي كتابة.
- **قبل الاستعادة:** نسخة تلقائية من الحالة الحالية في مجلد داخلي، ثم عرض ملخص (عدد الشعب والمعلمين والإصدارات والعام).
- **الاستعادة الآمنة:** كل الكتابة داخل Transaction واحدة. أي فشل يُلغي الكل، فتبقى البيانات الحالية كما هي.
- **التشفير الاختياري:** AES-256-GCM بمفتاح مشتق من كلمة المرور بـ PBKDF2 (عدد تكرارات يُحدد بالقياس على الجهاز، ولا يقل عن 210000 حسب توصيات OWASP الحالية). كلمة المرور لا تُحفظ في الملف ولا في التطبيق.
- **النقل:** اختيار مكان الحفظ عبر Storage Access Framework، والمشاركة عبر Intent.
- **BackupProvider:** واجهة في Domain، وتنفيذ محلي فقط الآن. أي مزامنة لاحقاً تنفّذ الواجهة نفسها.

### 9.3 إصدارات المخطط
- `schemaVersion` في الملف، و`version` في Room.
- الاستعادة من إصدار أقدم: تمر عبر Migration صريح للبيانات قبل الكتابة. إصدار أحدث من التطبيق: يُرفض مع رسالة "حدّث التطبيق".
- كل Migration يُختبر بـ `MigrationTestHelper`، مع ملف بيانات من كل إصدار سابق.

## 10. خطة الاختبارات والبيانات التجريبية

### 10.1 الاختبارات (ما هو منفّذ الآن محلياً، وما يلزم لاحقاً)
| المجال | الحالة | الاختبارات |
|---|---|---|
| محرك التعارضات | ✅ منفّذ (9 حالات + تطابق عشوائي 2000) | تعارض المعلم، تكرار الخانة، النصاب، التكليف، التوفر، المادة، الورديتان، المتتالي |
| المدقق | ✅ منفّذ | مسودة مقابل اعتماد، الإعداد، تطابق مع المحرك |
| فحص الجدوى | ✅ جزئياً | خانات الشعبة، نصاب المعلم |
| CSP | ✅ منفّذ | حل كامل، مهلة صفر، إلغاء، الحصص المقفلة، إعادة توزيع نطاقي، LNS، رفض فوري للإعداد |
| الجدولة الصلبة والمرنة | ✅ جزئياً | الجودة وأوزانها، التفضيلات، توازن الأعباء |
| المسودات والاعتماد الذري | ⏳ لم يُنفَّذ (يحتاج Room) | Transaction، تحديث شرطي، أرشفة الإصدار السابق |
| عزل الأعوام | ⏳ | استنساخ، الأعوام لا تتأثر بعضها |
| PDF العربي | ⏳ | فتح الملف، عدم كسر الكلمات، A4، أرقام صفحات |
| النسخ والاستعادة | ⏳ | نسخ ثم استعادة مطابقة تماماً، ملف تالف يُرفض، مخطط أقدم |
| الأداء على الهاتف | ⏳ | يحتاج جهازاً فعلياً |
| الواجهة | ⏳ | اختبارات Compose على الجهاز أو Robolectric |
| الورديات والتداخل | ✅ على مستوى Domain | يُكمَّل بالاختبار على قاعدة البيانات |

### 10.2 البيانات التجريبية (Seed)
المصدر: `DemoSchool.build` في الاختبارات فقط، وليس في الإنتاج.

**حساب عدد المعلمين (المعادلة المطلوبة):**
`عدد المعلمين ≥ (إجمالي الحصص ÷ متوسط النصاب) × 1.10`

- 12 شعبة (وضع الهامش): إجمالي الحصص 288، متوسط النصاب 20، فالنتيجة `288 ÷ 20 × 1.10 = 15.84`، أي 16 على الأقل.
- البنية الفعلية: 18 معلماً (12 معلم صف + 6 معلمي اختصاص). الزيادة سببها أن معلم الاختصاص يخدم مجموعة شعب ضمن وردية واحدة، فلا يكفي حساب المتوسط وحده.
- 18 شعبة: 432 حصة ⇒ `432 ÷ 20 × 1.10 = 23.76` ⇒ 24 على الأقل. البنية الفعلية 30.

**سيناريو الاستحالة:** `DemoSchool.build(gradeCount = 6, specialistNorm = 10)`. معلمو الاختصاص مكلفون بـ18 حصة لكل منهم ونصابهم 10، فيُرفض الإعداد فوراً بسبب واضح. هذا يختبر رسائل الفشل.

### 10.3 اختبارات مقترحة لم تُكتب بعد (على مستوى الواجهة والتخزين)
- إعادة التشغيل: البيانات تبقى كما هي بعد إغلاق التطبيق وفتحه.
- تعديل معلم بعد الاعتماد: يُنشئ مسودة، ويعرض التأثر، ولا يحذف الإصدار المعتمد.
- عزل الأعوام: تعديل صف في عام لا يغيّر الأعوام الأخرى.

## 11. المخاطر ومعالجتها

| الخطر | الاحتمال | الأثر | المعالجة |

## 12. أرقام معايير القبول (مقترحة، تُعتمد بعد القياس الفعلي)

| المعيار | الهدف | طريقة القياس |
|---|---|---|
| التوزيع التلقائي، 12 شعبة | ≤ 60 ثانية | `CspSolver.solveAll` بوقت الساعة (`System.nanoTime`) على هاتف متوسط (4 GB RAM)، 5 تكرارات، الأسوأ |
| التوزيع التلقائي، 18 شعبة | ≤ 120 ثانية | نفسه |
| الإلغاء يستجيب | ≤ 2 ثانية | قياس الزمن بين الضغط والعودة |
| استحالة معروفة | ≤ 2 ثانية | `Infeasible` مقاسة في الاختبار (حالياً ~20 ms) |
| جودة الحل | ≥ 80 | `QualityScorer` على بيانات الهامش |
| لا حل صلب في أي جدول معتمد | 0 | `ScheduleValidator.canApprove` |
| فتح شاشة جدول | ≤ 1 ثانية | Macrobenchmark أو قياس يدوي |
| PDF لجدول صف | ≤ 10 ثوانٍ | قياس الزمن للتوليد |
| PDF للمدرسة كاملة | ≤ 60 ثانية | نفسه |
| نسخ ثم استعادة | مطابقة 100% | مقارنة JSON بعد الاستعادة |
| ملف تالف | يُرفض دون مساس | اختبار بملف مقطوع ومعدَّل |
| تغطية Domain | ≥ 80% | JaCoCo عند توفره، وإلا ما نسبته الحالات المغطاة |

> ملاحظة: الأرقام في الجدول مقترحة. الأرقام المقاسة حالياً على بيانات Demo أقل بكثير، لكنها لا تُعد دليلاً قبل القياس على بيانات حقيقية وهاتف فعلي.

### ما يُبنى عبر GitHub Actions
- **في كل رفع:** تشغيل `scripts/test-domain.sh` (الاختبارات الخالصة)، ثم بناء Debug APK وتشغيل اختبارات الوحدة، ثم رفع APK كملف قابل للتنزيل.
- **لاحقاً:** توقيع Release عبر GitHub Secrets (keystore مشفّر بـ base64، وكلمات المرور)، ولا تُطلب كلمات المرور في المحادثة.
- **تجهيز Gradle دون Android Studio:** الـ workflow يثبّت Gradle بإصدار محدد، ويولّد wrapper داخل CI، فلا يُخزَّن `gradle-wrapper.jar` في المستودع.

## القرارات التي تحتاج موافقتك
1. المرحلة التالية هل تبدأ بتطبيق Android (المرحلة 1)، أم تُكمَل الاختبارات على قاعدة البيانات أولاً؟
2. أرقام القبول في القسم 12 مقترحة. هل تعتمدها أم تعدّلها بعد أول قياس على بيانات حقيقية؟
3. هل يلزم تشفير النسخ الاحتياطية من الإصدار الأول أم يُؤجَّل (P2 حسب الخطة)؟
4. الإسناد لمعلم الاختصاص عند امتلاء خانات معلم الصف: أيُقترح تلقائياً أم يبقى قراراً يدوياً؟
